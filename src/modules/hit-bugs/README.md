# 🪰 打苍蝇游戏模块

## 项目概述

这是一个基于 Canvas 2D 的打苍蝇小游戏，采用 React + TypeScript 技术栈开发。游戏讲述了一个人和兔子的趣味故事，通过点击苍蝇获得分数。

## 📄 各文件详细说明

### 1. `constants.ts` - 游戏常量配置（808字节）
**作用**：定义游戏中用到的所有常量、枚举和配置参数
- `GameState`：8种游戏状态的枚举（使用 as const 确保类型安全）
- `FLY_TYPES`：两种苍蝇的配置（普通10分，金色50分）
- `CONFIG`：全局配置（最大生命10、高分键名、粒子上限300）
- `ANIMATION_DURATIONS`：各种动画的持续时间配置

**技术细节**：
- 使用 `as const` 确保枚举值的不可变性
- 集中管理所有常量，便于维护和调整

### 2. `GameEngine.ts` - 游戏核心引擎（6955字节）
**作用**：管理游戏的核心逻辑和状态流转，是整个游戏的大脑

**核心功能**：
- **状态管理**：8种游戏状态的完整生命周期管理
- **数据结构**：GameData 接口封装所有游戏数据
- **事件处理**：
  - `handleHit()` - 处理苍蝇被击中
  - `handleMiss()` - 处理点击空处
- **特效管理**：
  - `addTransformEffect()` - 兔子变身白光特效
  - `addParticle()` - 粒子爆炸效果
- **状态转换逻辑**：完整的游戏流程控制

**设计亮点**：
- 使用私有属性保护内部状态
- 状态转换时自动初始化相关数据
- 完善的错误处理和边界情况考虑

**待补全功能**：

### 7. `utils/Fly.ts` - 苍蝇工具类
**作用**：处理苍蝇的核心逻辑，是游戏中最活跃的部分

**核心方法**：
- `create(W, H, difficulty)` - 从屏幕边缘随机生成苍蝇
  - 支持两种类型：普通苍蝇和金色苍蝇
  - 金色苍蝇生成概率随难度增加（8%~30%）
  - 初始朝向屏幕中心，带有随机偏移
  
- `update(fly, dt, W, H)` - 更新苍蝇位置
  - 正弦波飞行轨迹，模拟真实飞行
  - 金色苍蝇每1-1.5秒闪现一次（瞬移+变透明）
  - 边界检测，超出屏幕自动销毁
  
- `isHit(fly, x, y)` - 精确的点击检测
  - 圆形碰撞检测，放宽10像素增强手感
  - 返回布尔值表示是否命中

**技术亮点**：
- 使用 `FlyType` 枚举确保类型安全
- wobblePhase 实现自然的飞行摆动
- 闪现机制增加游戏挑战性

## 🎮 游戏设计思路

### 核心玩法设计
1. **基础交互**：点击苍蝇获得分数
2. **两种苍蝇**：普通苍蝇（10分）和金色苍蝇（50分）
3. **生命系统**：10条生命，点空扣除1条
4. **剧情流程**：开场 → 变身 → 游戏 → 结局（包含救场剧情）

### 状态机设计
```
IDLE(开场) → TRANSFORM(变身) → PLAYING(游戏)
    ↓              ↓                ↓
FAIL_CRY(失败)   BOMB(扔饮料)     BOMB(清场)
    ↓              ↓
HUG(抱起)       HUG(抱起)
    ↓
CURTAIN(幕布) → RESULT(结算)
```

### 🧠 技术选型思考过程

#### 1. 为什么选择 Canvas 2D 而不是 DOM 或框架？
**考虑因素**：
- **性能需求**：游戏需要同时渲染大量苍蝇和粒子效果
- **动画流畅度**：60fps 的流畅动画
- **自由度**：任意形状的渲染和特效
- **控制力**：精确的碰撞检测和坐标控制

**对比分析**：
- DOM：元素多时性能差，动画不够流畅
- React：虚拟 DOM 开销大，不适合频繁更新
- Canvas：直接控制像素，性能最优

#### 2. 为什么选择 TypeScript？
**问题场景**：
- 游戏状态复杂，类型定义量大
- 团队协作需要清晰接口
- 减少运行时错误

**解决方案**：
- 严格的类型检查
- 完整的接口定义
- 智能代码提示

#### 3. 架构设计思考
**分层架构**：
```
┌─────────────────┐
│   React UI层    │ ← 状态显示、用户交互
├─────────────────┤
│  Hook管理层     │ ← 状态同步、生命周期
├─────────────────┤
│  Canvas引擎层  │ ← 渲染循环、事件处理
├─────────────────┤
│  游戏逻辑层     │ ← 状态机、规则计算
└─────────────────┘
```

**设计原则**：
- 单一职责：每个模块只做一件事
- 依赖倒置：高层模块不依赖底层实现
- 开闭原则：对扩展开放，对修改关闭

## 🔧 实现难点与解决方案

### 1. 性能优化挑战
**问题**：大量苍蝇和粒子同时存在
```typescript
// 解决方案：对象池 + 限制数量
if (particles.length > CONFIG.MAX_PARTICLES) {
  particles = particles.slice(-CONFIG.MAX_PARTICLES);
}
```

### 2. 状态同步问题
**问题**：Canvas游戏状态与React UI状态不一致
```typescript
// 解决方案：使用Hook同步
const { engine } = useCanvasGame(canvasRef);
const state = engine?.getState();
```

### 3. 类型冲突解决
**问题**：GameState在多处定义
```typescript
// 解决方案：统一从constants导入
import { GameState } from '../constants'
```

### 4. 事件处理优化
**问题**：频繁的点击事件影响性能
```typescript
// 解决方案：事件委托 + 节流
```

## 📝 开发笔记

### 遇到的问题及解决
1. **模块导入问题**：TypeScript 的类型导入和值导入冲突
   - 解决方案：统一使用 `import type` 导入类型

2. **Canvas 适配问题**：不同屏幕尺寸的适配
   - 解决方案：使用 window.innerWidth/Height 和 DPR 缩放

3. **状态同步问题**：React 状态和游戏状态的同步
   - 解决方案：使用 Hook 在游戏循环中更新 React 状态

### 性能优化建议
1. 使用离屏 Canvas 预渲染静态内容
2. 实现虚拟化，只渲染可见区域的苍蝇
